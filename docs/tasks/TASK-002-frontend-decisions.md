# TASK-002 — Front end v0.1: review findings, record decisions, close the loop

Read `CLAUDE.md`, ADR-0001 and ADR-0002 first. TASK-001 produced `simprep audit` →
`findings.json` + `report.md`, and a manifest with a findings snapshot and a
`decisions` array. Nothing yet lets a human *make* those decisions comfortably, and
nothing checks that every blocking finding has one. This task builds both.

Status: **accepted** (maintainer, 2026-09-26: defaults accepted for every open
question; the resolved decisions are listed at the end of this file).

## Goal

A static page (GitHub Pages) where a user opens a structure file, its `findings.json`
and, optionally, a manifest; inspects each finding in a Mol* view; records a decision per
finding; defines regions of interest; and exports a schema-valid `manifest.json`. On the
Python side, `simprep` reads that manifest back and reports which findings still lack a
decision, so the prep stage (a later task) can refuse to run while any blocking finding
is undecided.

## Constraints carried over

- ADR-0002: the front end **consumes** `findings.json`; it never parses or audits
  structures itself and never re-computes severity. Mol* reads the structure only to
  display it.
- CLAUDE.md: plain HTML/JS, no build step (an ADR is required to add one); Mol* and ajv
  from a CDN at pinned exact versions; the front end never transforms coordinates; it
  records decisions.
- Nothing leaves the user's machine. Files are opened with a file picker / drag and
  drop and read locally; there is no server, no upload, no analytics.
- Tests must run without network (CI runs pytest inside `unshare --net`).

## Deliverables

### 1. ADR-0003: front-end architecture
Record: ES modules without a bundler; a pure-logic layer (no DOM, no Mol*) separated from
a thin UI layer; state model (loaded documents + decisions + regions, one immutable
object replaced on every change); file I/O only through the browser's file APIs; where
unsent work is kept (localStorage draft, keyed by input SHA-256, clearly labelled as
not the record); how pinned CDN versions are chosen and bumped. Include the options
considered and why.

### 2. `frontend/` static site
- **Open**: structure file (`.cif`, `.cif.gz`, `.pdb`) + `findings.json` (+ optional
  `manifest.json`). Validate `findings.json` and the manifest with ajv against the
  repository's `schema/*.schema.json` (served alongside the site; the same files the
  Python side uses, never a copy). Compute the structure's SHA-256 with WebCrypto over
  the file bytes exactly as opened (compressed or not), as `provenance.sha256_file` does,
  and **refuse** a structure whose hash differs from `findings.json` `input.sha256`,
  naming both hashes.
  Refuse a manifest whose `input.sha256` differs.
- **Findings panel**: grouped by rule family, sorted by effective severity; severity
  stripe and chip; base → effective shown when escalated; decided / undecided state;
  filters for severity, family and "undecided only".
- **Detail**: every evidence item rendered by type (units: Å, Å², °); atoms listed;
  source records shown verbatim; options with trade-offs and cost; recommended option and
  the recommendation basis; rule rationale; references as DOI links; `[VERIFY]` flags.
- **3D view**: Mol* at a pinned exact version, driven through MolViewSpec
  (`molstar.lib.extensions.mvs`). Selecting a finding highlights and focuses its anchor
  residues (for gaps: the flanking residues) and shows context (metal shell atoms, glycan
  attachment residue). Regions of interest drawn in their own colour.
- **Decisions**: choose an option, rationale (required), decided_by (required),
  timestamp set on save. Options with `requires_explicit_choice` need an extra,
  explicit confirmation step in the page (no `confirm()` dialogs). Option-specific
  parameters go in the decision's `parameters` object; v0.1 needs one:
  `specific_altloc` → `{"altloc": "<id>"}`, chosen from the altlocs in the evidence.
- **Regions**: create / rename / delete named residue sets, entered as residue labels
  (`A:45, A:46, A:84`); picking residues in the Mol* view is optional for v0.1
  (decision 2). After any
  region change the page shows that severities are stale until
  `simprep audit --manifest` is re-run (ADR-0002); it does not re-weight them itself.
- **Export**: a complete `manifest.json`: the loaded manifest (or one initialised from
  `findings.json` provenance and the knowledge-base defaults it records) + regions +
  decisions + the findings snapshot. Validated with ajv before the download is offered;
  validation errors are shown, not swallowed. Also a copy-to-clipboard fallback.
- **Demo**: a "Load example" button that opens 5FQL from the committed panel data
  (structure + a findings.json generated from it), so the page is usable without local
  files. The demo findings file is generated by a script, never hand-edited, and CI
  fails if it is stale.
- Works at phone width; keyboard reachable; visible focus; light and dark themes.

### 3. Python: decision coverage
- `simprep manifest status MANIFEST [--structure FILE]`: validates the manifest (schema,
  decisions against snapshot, input hash if the structure is given) and prints, per
  severity, decided / undecided counts and the list of undecided findings. Exit code 0
  when no blocking finding is undecided, 3 otherwise (documented), 2 on error.
- `simprep audit --manifest` keeps refusing a manifest whose decisions name findings
  that disappeared after a re-audit (e.g. after a knowledge-base change), as it does
  today (decision 4). The error must list **every** orphaned decision (finding id,
  option, decided_by), not just the first, and say how to resolve it (remove or
  re-decide them in the front end).
- `manifest status` lists decisions that use a `requires_explicit_choice` option
  separately, so they stay visible at review time (the schema already requires a
  rationale on every decision).

### 4. Tests (all offline)
- **Front-end logic** as pure ES modules tested with `node --test` (Node's built-in
  runner, no npm dependencies): state transitions, decision validation, region parsing
  (`A:45`, insertion codes `A:52A`, ranges `A:444-453`), manifest assembly, stale-severity
  flag, evidence formatting.
- **Cross-language contract**: a node script assembles manifests from the panel's
  findings files and writes them to a temporary directory; pytest validates them against
  `manifest.schema.json` and runs `simprep manifest status` on them. This checks the
  browser's output with the Python validator without a browser or network.
- **Python**: unit tests for `manifest status` (all decided, blocking undecided,
  unknown finding, wrong option, hash mismatch) and for the re-audit error listing all
  orphaned decisions (decision 4).
- Browser smoke test (Playwright, Mol* and ajv from CDN) is **not** in CI because it
  needs network; document how to run it locally and run it once before opening the PR,
  reporting the result.
- CI: add a Node 22 step for `node --test frontend/`; keep pytest under `unshare --net`.

### 5. Deployment
GitHub Actions workflow that publishes `frontend/` + `schema/` + the demo data to GitHub
Pages on pushes to `main` only. No secrets. Document the URL in the README.

## Acceptance criteria
- `node --test` and `pytest` pass locally and in CI, without network.
- Loading the 5FQL demo shows all 16 findings; selecting `metals/A:1551` focuses the Ca²⁺
  site in Mol*; recording decisions for every finding and exporting yields a manifest
  that passes `manifest.schema.json` in Python and makes `simprep manifest status` exit 0.
- Exporting with any blocking finding undecided makes `simprep manifest status` exit 3
  and list it.
- A structure whose SHA-256 differs from `findings.json` is refused with both hashes shown.
- A `requires_explicit_choice` option cannot be saved without the explicit confirmation.
- After a region edit the page marks severities as stale; re-running
  `simprep audit --manifest` on the exported manifest gives the escalated severities
  (demonstrated with the 5FQL active-site region: Ca²⁺ warn → blocking).
- ADR-0003 merged with the code.

## Out of scope
In-browser detection or severity re-weighting (ADR-0002; revisit as a separate task if
wanted), coordinate modification, multi-user or server-side storage, accounts,
parameterization, Colab modules, new rule families (including the covalent-contact rule
agreed for 1HZH, which gets its own task).

## Implementation notes from the TASK-001 prototype
A throwaway preview was built outside the repo (private artifact "5FQL Findings Review").
Lessons worth keeping:
- Never give the Mol* container `id="molstar"`: element IDs become `window` properties
  and shadow the `molstar` global, which breaks load-failure detection.
- MolViewSpec builder: `download → parse({format:"mmcif"}) → modelStructure →
  component({selector:[{auth_asym_id, auth_seq_id}, …]}) → representation → color`, then
  `.focus({})`; load with `viewer.loadMvsData(state, "mvsj", {replaceExisting: true})`.
  Findings carry auth numbering, which matches these selectors directly.
- Mol* 5.11.0 was current when the prototype was built; pin whatever is current at
  implementation time and record it in ADR-0003.
- Some static hosts do not serve `.cif`; GitHub Pages does, but the demo loader should
  not depend on the extension (read as text or bytes).

## Resolved decisions (maintainer, 2026-09-26)
1. **Users**: `decided_by` is free text in v0.1; no accounts or identity checks.
2. **Regions**: entering residue labels is required; picking residues in the Mol* view
   is optional for v0.1.
3. **Severity after region edits**: the page shows a stale-severity banner and never
   re-weights in the browser; re-running `simprep audit --manifest` is the only way to
   update severities (ADR-0002 option 3 stays open for a later task).
4. **Decisions orphaned by a re-audit**: remain a hard error, with a message listing
   every orphaned decision and how to resolve it.
5. **Exit codes of `simprep manifest status`**: 0 when every blocking finding is
   decided, 3 when any blocking finding is undecided, 2 on error; no extra flag.
6. **Hosting**: publish `frontend/` on GitHub Pages from `main`. The page holds no user
   data; structures and findings are opened locally and never uploaded.
